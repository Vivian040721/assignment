# 接口与联调约定

公共 schema 位于 `src/paper_agent/schemas.py`，机器可读定义位于 `contracts.schema.json`。02/05 协调修改后，必须通知上下游并更新测试。

## 三个 MCP 工具

| 工具 | 前置条件 | 主要输出 | 所有人必须保留的约束 |
|---|---|---|---|
| `search_and_select(idea, k=3, query="")` | 想法 3–4000 字符；k 1–10；query 至多 1000 字符 | 全局 run_id、来源统计、候选和 Top-k | 相关性筛选不能变成只挑可下载论文；live 筛选失败不伪装成模型成功 |
| `prepare_fulltexts(run_id)` | run.json 存在且模式一致 | 每篇 PDF/MD 路径和状态 | 仅下载公开链接；摘要不能冒充全文 |
| `generate_report(run_id)` | 已进行全文处理 | 单篇总结、报告路径、覆盖和错误 | 无全文不生成该篇全文总结；缺论文或阅读不全要 partial |

所有工具返回同一个 `RunResult` 结构，JSON 可序列化。论文 ID 在跨源去重后保持稳定；文件名使用 ID 哈希，避免 arXiv 旧 ID 的斜杠破坏目录。每个 run_id 独占产物目录。

## 状态和证据

- `selected`：筛选完成，不代表全文可得。
- `fulltexts_ready`：请求的 k 篇正文准备完成，不代表总结完成。
- `completed`：live 模式两源都有结果、k 篇全文和总结齐备，报告生成，未记录错误或部分阅读。仍需人工做内容质量验收。
- `demo_completed`：模拟样例的通信和文件链路成功，不代表真实 Agent 或论文效果。
- `partial`：保留所有可用结果，同时记录 errors、逐篇 failure_reason 和 evidence_coverage。

`trace.jsonl` 仅保存阶段、工具、短筛选依据、状态和时长；不保存 API key 或模型内部推理内容。`source_*.json` 是 API 结果规范化后的记录，03/04 后续可扩展原始响应归档。

## 测试样例

模拟样例在包内 `fixtures/`：两源各 3 条记录，合并前 6 条、去重后 4 条。默认 Top-3 产生 3 份模拟正文和模板总结。数据含 `DEMO` / `example.invalid` 标记，不应进入正式论文清单。

每个模块首交带：一条运行命令、一份输入、一份输出、已知失败情形。遇到公共接口变化，不通过临时新增字段绕过 `extra=forbid`；更新 schema、上下游和测试。

## 组长集成检查

1. 从主 Agent 入口启动，确认日志发现三个 MCP 工具。
2. 确认 run_id 在三次调用中一致。
3. 打开 run.json 核对来源数量、去重数量、ID、状态与覆盖。
4. 随机打开一份总结和报告，回到对应 Markdown 检查内容。
5. 检查失败用例：缺公开全文、无候选、无效模型 ID/JSON、下载错误或模型异常。
6. live 验收必须出现 `model_tool_call`，并保留真实来源与模型调用证据；demo 的 `scripted_demo` 不能代替。
