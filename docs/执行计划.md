建议 MVP：**arXiv + OpenAlex 两个来源；每源先取约 20 篇，去重初排后保留至多 15 篇供任务 Agent 筛选；默认 k=3；完成全文处理、3 篇总结和 1 份综合报告。优化选“并发处理”。** 数量不足时返回实际数量和原因，不补无关论文。完整流程稳定后才考虑 k=5。

任务文件没有明确要求训练模型、部署到公网、复杂网页、PPT 页数或报告字数。项目说明和答辩材料按课程实际提交规则准备。

## 2. 系统怎么搭

```text
研究想法
   ↓
主 Agent（解析用户意图，实际发起 MCP 工具调用）
   ↓ MCP client / server
自行编写的 MCP 服务
   ├─ arXiv 检索适配器 ─┐
   ├─ OpenAlex 适配器 ──┴→ 统一格式 → 去重 → 基础排序
   ├─ 内部任务 Agent：依据研究想法、标题、摘要筛选 Top-3
   ├─ 公开全文下载 → PDF 转 Markdown
   └─ 内部任务 Agent：单篇总结 → 综合研究报告
   ↓
主 Agent 返回论文列表、文件位置和运行摘要；演示入口展示过程
```

两处 Agent 可以使用相同模型，但职责、提示词和调用记录分开。任务 Agent 可以是一个封装类，承担“筛选、单篇总结、综合报告”三个任务，无需为此做复杂的多 Agent 通信。这里的任务 Agent 指作业中的模型工作者，不是要求实现 MCP 协议的异步 Tasks 功能。

**关键实现边界：**主 Agent 要有真实的模型工具调用；MCP 服务内部要有真实的任务 Agent 调用。普通 Python 脚本直接串函数可以用于开发自测，但不能替代最终的 Agent + MCP 演示。筛选时只看了标题和摘要，理由中就应标注依据为标题/摘要；全文总结必须在全文转换后进行。

### 技术建议

- 环境统一用 Python 3.11，第一天锁定依赖版本，所有人使用同一份锁文件。任务书写的是 Python 3.10+；核对时 MCP SDK 当前官方主线要求 3.11+，不要混用不同大版本的示例。[MCP SDK 官方仓库](https://github.com/modelcontextprotocol/python-sdk)
- MCP 优先用本机 stdio，减少部署工作；标准输出留给协议消息，调试信息写日志文件或 stderr。使用 SDK 支持的客户端和服务端，不自行仿制协议。
- arXiv 用 API / arxiv.py；OpenAlex 用 HTTP API。当天验证真实检索；OpenAlex 提前准备免费 key、检查额度与限流，不把收费内容下载作为完成前提。[OpenAlex 认证说明](https://help.openalex.org/api/authentication/)
- 基础排序采用轻量 SentenceTransformer 对“想法”和“标题+摘要”计算相似度；模型只加载一次，模型名称和版本写入配置。若模型下载受阻，先用可解释的关键词匹配跑通，再按约定补上语义排序。
- PDF 转换使用 PyMuPDF4LLM，抽检双栏正文、标题和表格；不把复杂公式完全还原当作本次验收前提。[PyMuPDF4LLM 官方文档](https://pymupdf.readthedocs.io/en/latest/pymupdf4llm/)
- 默认采用 CPU 运行流程、模型 API 完成 Agent 任务的方案，无需专门准备 24GB 显卡或 CUDA。原文把 24GB 显存写为设备建议；若课程额外要求本地模型，01 号先验证现有设备完成工具调用与总结后再冻结方案。

## 5. 第一天必须约定好的接口

### 5.1 统一论文记录

建议由 02 与 05 共同冻结字段，并交 01、03、04、06、07、08 使用：

```text
PaperRecord:
  paper_id                # 项目内稳定 ID
  title, authors, year
  abstract                # 允许缺失，不伪造
  doi, arxiv_id           # 允许缺失；arXiv 版本信息单独保存
  sources[]               # 合并后保留全部来源
  source_records[]        # 各源原始 ID/URL，便于核查
  landing_url, oa_pdf_url  # 论文页面与公开 PDF 分开
  base_score

SelectedPaper:
  paper_id, rank, selection_reason, selection_basis

PaperArtifact:
  paper_id, pdf_path, markdown_path, summary_path
  fulltext_status, failure_reason, evidence_coverage

RunResult:
  run_id, input_idea, query, top_k
  source_counts, merged_count, dedup_count, candidate_count
  selected_papers[], artifacts[], report_path
  timings, status, errors[]
```

05 的去重顺序：规范化 DOI 精确匹配 → arXiv 基础 ID 匹配 → 标题规范化并结合作者/年份判断。保留版本和来源；标题相似本身不足以证明是同一篇论文。

### 5.2 建议暴露的 MCP 工具

1. `search_and_select(idea, k)`：两源检索、去重、初排，并由服务内部任务 Agent 二次筛选；返回 run_id、论文清单、理由和各源数量。
2. `prepare_fulltexts(run_id)`：下载公开全文、转换 Markdown；返回逐篇状态和文件位置。
3. `generate_report(run_id)`：服务内部任务 Agent 读取已转换内容，输出单篇总结和综合报告；返回产物清单、证据覆盖和时长。

这是小组接口建议，不是 MCP SDK 的内置方法。主 Agent 通过工具 schema 发起调用；同一 run_id 串起日志和产物，避免几个人的输出混在一起。所有工具返回可序列化的结构和明确错误；服务内限制输入长度、k 与重试次数。

## 6. 优化如何做，结果如何比较

### 6.1 推荐只主攻并发处理

基线：逐篇处理论文，完成一篇的转换和总结后再处理下一篇。

优化：在不改变检索、初排、筛选规则和提示词的前提下，允许独立论文的处理并发，先把并发上限设为 3；文档解析若是阻塞操作，放入受限线程/进程或预处理阶段，不能只套 `async` 就宣称并发。综合报告仍等待单篇结果完成后生成。

线上下载与 API 请求设置每源限速和退避。arXiv 旧版 API 官方要求单连接、相邻请求至少间隔 3 秒；全组共享限速约束。并发优化优先做本地转换/模型请求等独立任务，不靠加大 arXiv API 请求频率获得收益。[arXiv API 使用条款](https://info.arxiv.org/help/api/tou.html)

### 6.2 两组验证，分清局部优化和完整系统

**A. 可控的优化对比：**

1. 09 号在 23 日预先写好 5 条具体研究想法，例如 RAG 幻觉、Agent 长期记忆、工具调用可靠性、长上下文推理、低成本多 Agent 协作；要求包含任务、方法或约束，避免只写一个宽泛词。
2. 26 日基线通过后，为每条想法冻结候选、Top-3 和对应已下载 PDF；记录论文 ID、文件哈希和版本。样例若全文不齐，记录原因；补充可处理样例需在优化实验前完成并留痕。
3. 在同一设备、同一模型/提示词/温度、相同全文输入上，比较串行与并发的“Markdown 转换 + 单篇总结”阶段；模型先统一预热。
4. 每条想法每种模式运行 3 次，交替先后顺序；共 5×2×3=30 次阶段运行。摘要/Markdown 结果缓存对两种模式都禁用；PDF 都从相同本地快照读取。
5. 记录每次模式、run_id、论文 ID、耗时、成功/失败、重试、输出验证结果和可获得的 token 用量。报告中位耗时、加速比以及最小/最大值；小样本不做普遍性能结论。
6. 明确标注这是固定全文输入下的处理阶段优化，不把回放检索或预下载耗时计作实时端到端收益。

**B. 真实完整流程验证：**

5 条研究想法各做至少一次真实调用，记录从主 Agent 接收输入到综合报告写完的总时长，以及检索、筛选、下载、转换、总结、综合报告各阶段时长。记录来源请求和全文失败，不把历史回放计入在线成功率。网络故障回放可以保障展示，但必须标明“历史运行”。

### 6.3 指标定义

- 阶段加速比 = 串行阶段中位耗时 / 并发阶段中位耗时。大于 1 才表示在该测量条件下变快。
- 阶段成功率 = 完成同一批全部论文处理且输出校验通过的运行数 / 全部尝试运行数。
- 端到端完整成功率 = 两源检索均成功、Top-3 合法、3 篇全文转换与总结成功、综合报告生成并通过校验的想法数 / 全部真实尝试想法数。部分完成另外统计，不能算完整成功。
- 输出校验至少包括：论文 ID 一致、文件非空、总结章节齐全、无明显跨论文串写、报告引用可追溯。09/10 抽检，不能仅以接口 HTTP 成功判定成功。
- 可增加人工相关性抽检：两名成员独立给 Top-3 标注相关/不相关，争议讨论后记录；样本少、非专家标注时注明局限。并发方案的主评价仍是耗时和成功率。

可预设内部优化目标为阶段加速比 ≥1.2 且成功率不下降，但这是工作目标，不是已获得结果，也不是作业规定阈值。未达到时照实说明瓶颈，不编造提升百分比。

## 8. 报告内容与演示方式

单篇总结建议固定为：论文信息与来源、研究问题、核心方法、实验/数据与实际报告的结论、局限、与用户想法的关系、正文依据位置。综合研究报告至少包括：用户想法拆解、检索与筛选方式、论文比较表、共同结论与分歧、可借鉴方案、证据不足处和下一步验证建议、参考文献。生成的研究建议必须与论文已经证实的结果区分。

演示建议按课程允许时长压缩成以下顺序，5–8 分钟只是排练建议：

1. 输入一个具体研究想法，展示主 Agent 发出的 MCP 工具名和参数。
2. 展示两个来源的检索数量、合并去重数量、基础排序候选。
3. 展示 MCP 服务内部任务 Agent 的 Top-3 和简短筛选依据。
4. 打开对应的公开全文链接、本地 Markdown 和单篇总结。
5. 展示综合报告，随机抽一条结论回到论文核查。
6. 展示总耗时与分阶段耗时，以及串行/并发对照数据。

真实运行若耗时较长，现场展示实时开始与进度，再打开已完成的真实历史运行；说明两者各自的 run_id 和状态。预录视频、历史结果都可备份，但不能声称是刚刚完成的在线运行。
