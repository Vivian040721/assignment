## 4. Sentence-BERT + RRF 的实际接入

### 4.1 模型与启用方式

- 模型：`sentence-transformers/all-MiniLM-L6-v2`。
- 默认仍是 `ranker=keyword`；未覆盖用户设置。语义模式通过进程级环境变量 `PAPER_AGENT_RANKER=semantic` 启用，现有 `Settings`、`main_agent.server_environment` 和 MCP 服务链路会沿用该值。
- 依赖已在 `.venv-v2` 实际安装：`sentence-transformers 5.7.0`、`torch 2.14.1`、`transformers 5.20.2`、`huggingface-hub 2.3.0` 及相应传递依赖。`numpy` 等已有包未被无故升级。
- 本地模型缓存已存在：`C:\Users\徐志鹏\.cache\huggingface\hub\models--sentence-transformers--all-MiniLM-L6-v2`（快照 `1110a243fdf4706b3f48f1d95db1a4f5529b4d41` 含 `model.safetensors`）。
- 在用户明确要求停止探针之前，曾用缓存做过一次模型加载/编码检查（加载约 38.3 秒，输出 2×384，归一化向量余弦约 0.6215）。收到停止边界后未再运行任何模型编码、测试或研究调用。
- 加载使用 `SentenceTransformer(..., local_files_only=True)`，不会在检索线程里触发网络下载；缓存缺失会走记录在案的降级。

### 4.2 顺序与排名语义

实际顺序：

```text
arXiv + OpenAlex 双源检索
→ 合并、去重、keyword_coverage_v1 初排
→ 全部去重候选的 Sentence-BERT 编码 + RRF
→ merged_candidate_limit 截断
→ Selector 的 candidate_limit 与真实 LLM Top-k
```

- 不在截断后才做语义排序；语义排序只处理本次真实检索得到的候选，不增加召回源。
- `initial_score` 仍保留原关键词 0–1 分；`final_score` 仍只保留 LLM 分。RRF 分和余弦不写入这两个字段。
- RRF 固定为 `0.5/(60+keyword_rank) + 0.5/(60+semantic_rank)`，排名从 1 开始；同分按原关键词排名、再按 `paper_id` 稳定排序。本轮未调参，不宣称权重最优。
- `ranking_details` 保留：`keyword_rank`、`semantic_rank`、`cosine_similarity`、`rrf_rank`、`rrf_score`、`rrf_k`、`rrf_weights`、`model_name` 和“RRF 不是概率”的语义说明。
- 候选 `rank` 的含义：keyword 模式下是候选初排名次；semantic 模式下是 RRF 候选名次；被 LLM 选中的副本 `rank` 仍按原逻辑改为 LLM 入选名次。原始关键词名次另存 `ranking_details.keyword_rank`，前端分别显示。
- Selector 输入获得紧凑 ranking 对象，但选择逻辑和最终 JSON 契约未替换为规则或相似度 Top-k。

### 4.3 线程、缓存与降级

- 模型加载和 `encode()` 都在 `asyncio.to_thread()` 工作线程执行，不阻塞事件循环。
- 进程级惰性模型单例；模型加载锁和编码锁分离，避免重复加载和不安全并发 encode。
- 进程内有界 LRU 向量缓存（上限 4096），键为模型标识 + 查询/标题摘要内容哈希；不持久化全文、不新增向量数据库。
- 只在整个候选集的向量和名次都算完后才更新论文对象；任何加载/编码/融合失败都回退完整原关键词顺序，不留下半套语义 metadata。
- 运行指标 `metrics.ranking` 记录 requested/actual ranker、模型、候选数、编码数、缓存命中、加载/编码/总耗时、降级子原因、中文提示和截断前后候选数。
- 稳定降级子原因：`dependency_missing`、`model_load_failed`、`embedding_failed`、`empty_query`、`no_candidates`、`semantic_rerank_failed`。实际降级不会被标成 successful semantic。
- 事件流记录 `semantic_ranker` 的 `start`、`finish` 或 `fallback`，并携带安全计数/原因；不暴露第三方异常正文。

## 5. 总结与报告的实际修复

### 5.1 从已有失败记录得到的判断

只读检查了 `data/validation/v021/stress/` 和 `data/validation/v021/report-regeneration*`。实际现象包括：

- 多个运行有 8 篇 Markdown，但 `fulltext_summary_count=0`；主要错误是 `invalid_model_output` 和随之而来的 `partial_summary`。
- 失败记录缺少字段/证据定位，所有问题都收敛成同一条错误信息。
- 报告在 64k 输入预算下出现 `llm_budget`，或 response 被截断/不一致；报告输入包含大量总结字段。
- 报告引用/标题/字段与小规模重生成记录存在失配。

### 5.2 JSON 与 schema

- `llm.py` 的 JSON 解析现在只做确定性清理：允许围栏和前后说明文字；拒绝多个 JSON 对象、对象/数组嵌套、顶层数组和无法确定为单一对象的尾部内容。`raw_decode` 不再静默忽略第二个值。
- `LLMOutputError` 增加稳定 `reason`（如 `output_truncated`、`json_parse_failed`），用于安全诊断；不记录服务端正文。
- 总结/报告 schema 仍为严格 Pydantic 校验；错误会带安全 `details`：字段路径/错误类型、证据索引、quote 字符数、页码、段 ID、分块 ID 等。不记录引文原文、凭据或第三方异常正文。

### 5.3 总结证据与 scope

- chunk 输入包含稳定的 `segment_id`；模型可回填 `source_segment_id`，程序用该段核验。
- 引用仍必须在一个实际提供的 segment 内逐字命中（仅做 NFKC + 空白折叠），不接受跨 segment 拼接通过，也不能用 `page_number=null` 绕过边界。跨边界引用会被诊断，并在有限修复中要求缩短原文。
- 页码/章节仍严格校验；模型给 null 时只会在单一权威 segment 能确定页码时补页码，否则保持 null。未知页不伪造。
- `summary_scope` 仍由实际 Markdown、页码映射和全文完整性决定；`fulltext_quality.complete` 不满足时不能升级为全文。部分全文、漏读分块仍保留 `partial_fulltext`/`partial_summary`。
- `invalid_model_output` 仍保留原机器码；细节以 `ErrorInfo.details` 记录，不删除错误。
- 对未读/失败分块，`partial_summary` details 记录 analyzed/total/selected、未读 chunk ID、失败 chunk ID。
- 为减少输出截断，提示限制每 chunk 最多 6 条证据、quote 280 字符、每个数组最多 8 项；不修改用户模型/预算配置。

### 5.4 merge 证据：选择已校验 ID，程序还原完整记录

- merge 提示提供 `verified_evidence` 目录，每条带 `evidence_id`；模型输出证据时优先使用只含 `evidence_id` 的对象。
- 程序按 ID 还原原来通过 chunk 校验的完整记录（paper_id、page_number、section、quote、claim、evidence_type），不要求模型重抄 claim，也不忽略 claim。
- 兼容“复制完整记录”的输出，但要求每个字段与某条已校验记录**完全一致**；出现未知 ID、重复 ID、额外字段或不匹配记录时，merge 明确失败，不用过滤/静默删除来通过。
- merge 失败时保留通过校验的各分块笔记并写明确 warning；最终证据集保留全部已校验记录，不因模型只选子集而丢失审计证据。
- 最终 summary 仍按实际 scope 保存；有错误时 `fulltext_summary_count` 不计为全文成功。

### 5.5 预算内有限修复

- 每个 `summarize_paper` 和每个 `generate_report` 最多使用一次反馈修复；只有 `llm_max_retries > 0` 时启用，并受现有 ChatClient 请求/token 预算和输入 `_fits` 约束。
- 修复请求只附带安全校验反馈，不重发非法原文，不扩大总重试或预算；鉴权、预算和传输错误不重复请求。
- 修复成功会写明确 warning（recovered 诊断），不伪造错误已消失；修复失败仍保留 `invalid_model_output`/`llm_budget`/`llm_failed` 及首次/第二次子原因。

### 5.6 报告契约、预算压缩与 partial

- 报告提示现在明确：`allowed_paper_ids`、`expected_references`、必须包含且仅包含所有实际总结的 ID 与精确标题、`[paper_id]` 引用格式、comparison 行必须有 `paper_ids`、输出简洁上限。
- 校验覆盖：引用 ID 集合、重复 ID、未知 ID、标题失配（仅容忍空白/大小写差异，最终使用真实标题）、正文内引用、comparison 行 ID、多篇报告必需章节。
- 报告仍只使用 `summary_scope != failed` 且有研究问题的总结；失败或不可用总结不进入 references。
- 当完整报告输入超过现有 `report_input_token_budget`/`llm_input_token_budget` 时，按级别 1–3 做**有界摘录**，保留所有论文、references 和 scopes，并在 `compacted_fields` 记录被省略的字段/条目；完整内容仍在单篇 summary artifact 中。
- **只要使用有界摘录**，就追加 `partial_report` 错误和明确的 `partial_reason`，报告在 live 运行中 `report_valid=false`、运行状态为 partial；仍继续尝试生成可用报告。没有提高预算，也没有把省略后的输入算作完整报告。
- 报告仍保留 `partial_report` 机器码；输入压缩的 `partial_report.details.reason = report_input_compacted`，前端显示为“部分报告（输入使用了有界摘录）”。
- 报告生成仍由证据决定：`report_valid` 不因修复或界面而放宽；`references` 只来自实际成功可用总结。

### 11.1 单篇报告改为深度研究笔记

- `PaperSummary` 新增可选 `overview`（一段全文概览）和 `deep_analysis`（Markdown 深度分析），同时在 `shared/contracts.ts` 补齐类型。旧 summary 没有这两个字段时按默认空值加载。
- `SUMMARY_SYSTEM` 现在要求模型输出 `overview` 和 `deep_analysis`：
  - overview 为约 120–220 字的一段话，概括论文问题、机制、证据和结论。
  - deep_analysis 为约 900–1800 字的中文研究笔记，包含问题、机制、实验/证据、批判性判断、与研究问题的关系等 `##` 小节。
  - 明确要求不要输出原文证据列表、阅读/生成限制、系统状态、文件路径或泛化套话；不得编造数字、实验或引用。
- `_summary_markdown` 改为：标题、全文概览、deep_analysis。**删除原文证据、阅读与生成限制、状态章节**。旧 summary 或 merge 未返回深度分析时，回退到结构化的研究问题/方法/实验/结论/系统推断/未验证设想/局限/关系章节。
- `_strip_forbidden_sections` 在保存 summary 前确定性移除 deep_analysis 中误生成的“原文证据”“阅读与生成限制”“生成限制”“系统状态”“报告状态”“全文概览”小节；这不仅是提示词约束。
- 前端论文详情：
  - 把原来的“总结范围”小字框改为“全文概览”卡片，显示一段 overview（缺失时回退 core_idea/relevance）。
  - 单篇正文优先使用 `deep_analysis`，避免与概览卡片重复。
  - 移除摘要 warnings、全文提取限制等阅读限制展示；只有真正的 summary errors 仍以折叠“校验状态”保留。
  - 移除重复的结构化 `SummaryFacts` 卡片，正文只保留研究笔记 Markdown。
- 相关限制适当放宽：`max_chunks` 默认从 12 调整为 16（环境变量仍可覆盖）；summary 允许最多 10 条方法/实验/结论/局限，内部证据上限 5 条，以给深度叙述留出输出空间。没有提高模型请求/token 总预算。
